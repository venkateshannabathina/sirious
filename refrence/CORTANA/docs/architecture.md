# CORTANA architecture

## Document status

This document records the application that exists today and the safe direction for reorganizing it. The backend has begun a low-risk extraction into the current `backend` package. Later target modules and shared configuration described below are still a plan and have not been implemented yet.

The immediate compatibility rule is simple: preserve behavior and public URLs before moving code. Structural cleanup must not silently remove character, animation, face, voice, camera, Photo Booth, Expression Creator, or World Editor functionality.

## Current runtime

CORTANA is a browser-based Three.js application served by a single FastAPI process. The root `app.py` is now a compatibility entry point for the extracted backend package.

```text
Browser
  └─ frontend/index.html
       ├─ frontend/libs/*
       ├─ frontend/style.css
       ├─ frontend/app.js
       ├─ model/cc3/cc3_master.glb
       ├─ model/cc3/animations/*.glb
       ├─ GET/PUT /api/world
       └─ POST /api/chat
            ├─ Groq or OpenAI
            ├─ Edge TTS
            └─ GET /api/audio/{filename}

app.py compatibility entry point
  └─ backend/main.py FastAPI assembly
       ├─ backend/config.py
       ├─ backend/schemas.py
       ├─ backend/chat_service.py
       ├─ backend/lip_sync.py
       ├─ backend/world_store.py
       ├─ /model/cc3 static mount
       └─ / frontend static mount
```

### Current source boundaries

| Path | Current responsibility |
| --- | --- |
| `app.py` | Compatibility entry point that exports `backend.main:app` and starts Uvicorn when run directly |
| `backend/config.py` | Environment, paths, model names, host/port/reload, voice, and allowed CORS origins |
| `backend/schemas.py` | Validated chat and world API models |
| `backend/chat_service.py` | Provider routing, prompt, bounded voice controls, fallback response, audio retention, and speech orchestration |
| `backend/lip_sync.py` | CC3 viseme conversion and Edge TTS word-boundary timeline generation |
| `backend/world_store.py` | Default world and atomic JSON persistence |
| `backend/main.py` | FastAPI assembly, health/world/chat/audio routes, filename validation, and restricted static mounts |
| `frontend/index.html` | Complete application shell, settings, Studio, Photo Booth, Expression Creator SVG, World Editor, and chat markup |
| `frontend/app.js` | Rendering, physics, character loading, materials, animation, locomotion, camera, face systems, Studio tools, world editing, audio, chat, and debug instrumentation |
| `frontend/style.css` | Current active application and feature styling |
| `frontend/styles/*.css` | Active additive monochrome foundation split into tokens, shell, Studio, rig, and responsive layers |
| `model/cc3` | Runtime character, baked animations, and currently generated diagnostics |
| `model/test` | Local source FBX, Blender textures, animation inputs, and experiments; not required by the browser runtime |
| `data/world.json` | Current mutable world document |
| `temp_audio` | Current transient MP3 output |
| `tools` | Blender-based export, retarget, bake, and diagnostic scripts |

## Preserved public URL contract

These logical URLs must continue working through the reorganization. Cache-busting query strings may eventually be generated by a build system, but the underlying behavior must remain compatible.

| Method | URL | Purpose |
| --- | --- | --- |
| `GET` | `/` | Main application |
| `GET` | `/style.css` | Current stylesheet |
| `GET` | `/app.js` | Current browser application |
| `GET` | `/libs/*` | Vendored browser dependencies |
| `GET` | `/img/*` | Browser image and HDR assets |
| `GET` | `/model/cc3/cc3_master.glb` | Runtime CC3 character |
| `GET` | `/model/cc3/animations/*.glb` | Baked idle and locomotion clips |
| `GET` | `/api/health` | Report application, frontend, and character-asset readiness |
| `GET` | `/api/docs` | Current FastAPI schema documentation |
| `GET` | `/api/world` | Load the saved world |
| `PUT` | `/api/world` | Validate and save the world |
| `DELETE` | `/api/world` | Reset the saved world; this exists server-side but is not currently called by the main client |
| `POST` | `/api/chat` | Generate companion response, emotion metadata, speech, and lip-sync cues |
| `GET` | `/api/audio/{filename}` | Serve generated speech audio |

The browser also persists a custom camera view in local storage using `cortana.camera.customView.v1`.

## Current shared contracts

The following data crosses subsystem boundaries and must be treated as versioned contracts:

- World document version, environment values, object types, and transforms.
- CC3 character path, animation filenames, clip names, and nominal movement speeds.
- CC3/Mixamo bone names and aliases.
- Facial morph names, speech visemes, tongue cues, and lip-sync timeline version.
- Chat response fields such as emotion, intensity, audio URL, and transition duration.
- DOM IDs and `data-*` attributes consumed directly by `frontend/app.js`.
- Debug state exposed through `window.__cc3Debug` and `document.body.dataset.cc3DebugState`.

Some of these contracts are currently duplicated across Python, JavaScript, HTML, and Blender scripts. Centralizing them is a planned task, not a completed one.

## Known architectural risks

- The browser application shares a large global mutable state and one render loop.
- The default world structure is represented independently in Python and JavaScript.
- Animation and bone mapping data is repeated between browser and Blender tooling.
- World and audio runtime data still write inside the project tree instead of configurable persistent storage.
- API routes still live together in `backend/main.py`; route modules remain a later extraction if the surface grows.
- Provider and TTS calls do not yet define explicit network timeouts.
- Inactive experimental code remains beside live code and needs coverage before removal.
- Optional DOM lookups can hide markup-to-code drift instead of failing clearly.

## Staged target architecture

The current extracted foundations are:

```text
app.py
backend/
  config.py
  schemas.py
  chat_service.py
  lip_sync.py
  world_store.py
  main.py

frontend/styles/
  tokens.css
  shell.css
  studio.css
  rig.css
  responsive.css
```

The remaining intended direction is:

```text
config/
  characters/cc3.json
  ui/shades.json
  world-default.json

backend/
  api/routes/               # planned only if route growth warrants it
  storage/                  # planned persistent-store adapters

web/
  index.html
  src/
    core/
    engine/
    character/
    face/
    features/
    ui/
  styles/

public/
  model/cc3/
  images/

tools/blender/
tests/
docs/
var/
```

The `config`, `web`, `public`, test, and persistent-storage layout remains a target. The five additive UI stylesheets are active after legacy `style.css` in this order: tokens, shell, Studio, rig, responsive. Migration should proceed in this order:

1. Record current behavior and add regression coverage.
2. Verify the new `/model/cc3` asset boundary and backend compatibility entry point.
3. Centralize shared character, animation, world-default, and shade contracts.
4. Add persistent storage adapters behind the existing world/audio behavior.
5. Extract frontend domains behind the existing bootstrap and render loop.
6. Continue the monochrome UI system after interaction coverage is stable.
7. Optimize and package assets only after visual comparison exists.

## Change guardrails

- Make one subsystem move per change set.
- Keep a compatibility entry point while modules are extracted.
- Do not rename public URLs and move files in the same unverified step.
- Do not delete inactive code until a search and runtime test prove it is unused.
- Do not optimize the CC3 GLB until facial morphs, skinning, materials, and animation are visually compared.
- Do not use color alone to communicate rig-control type or application state.
- Every stage must pass the checklist in `docs/qa-checklist.md`.
